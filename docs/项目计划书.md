# 项目计划书：面向生产环境的 Spring 生态 RAG 知识库问答系统

**项目代号**：SpringKB-RAG
**技术基线**：Spring Boot 4.0.x + Spring AI 2.0.x + PostgreSQL 16 + pgvector
**定位**：一个具备版本管理与权威性排序能力的检索增强生成知识库，以 Spring Boot 3.2/3.3 官方文档与 Stack Overflow 社区问答为知识源，模拟企业技术文档治理场景。
**目标**：解决裸 RAG 在真实组织中“版本污染”与“来源可信度混杂”两个核心工程问题，并验证工程化 RAG 在有限数据规模下的可行性与边界。

## 一、项目背景与问题定义

### 1.1 为什么不做通用文档问答

裸 RAG（上传文档 → 向量检索 → 拼接 prompt → 调模型）在 Demo 层面已经泛滥。面试官看到“接入了大模型做了个问答”不会产生任何区分度。真实企业场景中，RAG 落地的障碍不在模型能力，而在**知识治理**。

### 1.2 本项目的两个核心问题

**问题一：版本污染**。技术文档持续迭代，旧版本向量若不清理，用户询问新版本行为时可能召回旧版答案，产生“看似有据、实则过期”的错误回答。Spring Boot 3.2 与 3.3 存在行为差异，恰好构成天然的版本对比测试集。

**问题二：来源权威性混杂**。官方文档与社区问答的语义相似度分布不同：社区答案往往更贴合口语化提问，相似度分数可能更高，但权威性低于官方文档。若仅按向量相似度排序，系统会优先返回“高赞但非权威”的答案。

**为什么这个项目有生产价值**：企业 RAG 的第一道坎不是模型不够强，而是“不该被检索到的内容不能被检索到”（版本隔离）以及“检索到的内容需要按权威性分级”（可信度排序）。这两个问题在任何有权限边界和文档迭代的组织中都存在，与数据规模无关。

## 二、知识库数据源

| 来源                 | 版本/范围                                           | 标识字段                                 | 用途                     |
| -------------------- | --------------------------------------------------- | ---------------------------------------- | ------------------------ |
| Spring Boot 官方文档 | 3.2.x 与 3.3.x 的 `web`、`data`、`howto` 章节 | `source=official`, `version=3.2/3.3` | 权威基线，版本对比       |
| Stack Overflow       | `spring-boot` 标签，答案评分 ≥5，2023 年后       | `source=community`, `so_score`       | 社区补充，可信度加权测试 |

**数据量目标**：官方文档约 50-100 个 chunk，SO 问答约 200-500 条。不追求规模，追求**可验证的版本差异覆盖**。

**获取方式**：

- Spring 文档：Jsoup 抓取 HTML 并转纯文本（官方无 PDF 下载）。
- Stack Overflow：通过 Stack Exchange Data Explorer (SEDE) 执行 SQL 导出 CSV，无需爬虫反爬处理。

## 三、核心功能设计（三个差异化能力）

### 3.1 版本过滤检索

**行为**：用户查询时指定目标版本（3.2 或 3.3），系统仅从该版本的活跃文档中检索，不召回其他版本内容。

**技术实现**：向量检索请求携带 metadata filter，在 pgvector 查询层执行过滤。pgvector 的向量列与 `source_type`、`version`、`active` 等元数据列在同一张表中，过滤条件就是普通 `WHERE` 子句，天然保证一致性与准确性。Spring AI 的 `VectorStore` 支持 filter expression，配合 pgvector 的 metadata 索引可高效完成。

### 3.2 来源权威性加权

**行为**：检索返回候选后，对 `official` 来源的文档施加权重加成，使其排序优先于语义相似度略高但来源为 `community` 的结果。

**技术实现**：初检取 topK×3 候选，按 `score + (isOfficial ? boost : 0)` 重排序，取前 5 送入生成阶段。boost 值初始设 0.15，后续用验证用例微调。

### 3.3 引用溯源与无答案兜底

**行为**：生成的回答中每个关键结论标注引用编号，前端可展开查看原文片段。当检索结果最高相似度低于阈值时，不调用 Chat 模型，直接返回“知识库中未找到相关答案”。

**技术实现**：chunk metadata 保留 `source_title`、`section`、`so_question_id`。Prompt 中强制要求标注 `[1][2]`。兜底阈值初始设 0.65（余弦相似度），通过测试集校准。

## 七、面试话术框架

**开场**：不说“我用了 Spring AI”，说“我调研了企业 RAG 落地的障碍，发现两个比模型选型更关键的问题：文档版本迭代导致旧答案污染，以及官方文档与社区答案的权威性差异被语义相似度掩盖。”

**展开**：每个问题 → 为什么裸 RAG 解决不了 → 我的方案 → 验证结果 → 踩过的坑。

**差异化回答**（面对“和低代码平台区别”）：那些平台解决“快速搭一个能用的”，我解决“在文档持续变化、来源参差的条件下，答案不会悄悄出错”。我的检索带版本 filter，排序有权重，兜底不硬编。

**版本选择说明**（面对“为什么用 Boot 4”）：Spring AI 2.0 在设计上就是面向 Boot 4 的，1.x 搭配 Boot 3.x 的时代已经过去。作为新项目没有历史包袱，直接上 4.0 比先用 3.x 再迁移更合理。过程中确实遇到了 API 变化的问题，但通过官方文档都解决了。

## 八、已知限制（主动写进 README）

1. **Spring AI 2.0 生态资料相对较少**：网上大量 Spring AI 教程基于 1.x，2.0 的 API 变化可能导致示例代码无法直接运行。本项目以官方参考文档和 Javadoc 为主要依据。
2. **Chunking 策略较粗**：使用固定 token 窗口，未做语义分块。在有限语料下调参收益低，留作后续优化。
3. **加权系数未做系统调优**：boost=0.15 基于少量用例手调，未做网格搜索。面试时可说“我知道需要更大规模的标注集来校准”。
4. **pgvector 的扩展上限**：当前数据量（几十到几百 chunk）远低于 pgvector 的百万级舒适区，但若未来数据量增长至千万级以上，需评估迁移至 Qdrant 或 Milvus。

**一句话总结**：不做“又一个 RAG Demo”，做“一个能说清楚企业 RAG 为什么容易出错、并且用代码验证了怎么不出错”的项目。技术底座使用当前官方支持的 Boot 4 + Spring AI 2.0 组合，核心价值在于版本治理与权威性排序的工程实现，而非模型调用的熟练度。
