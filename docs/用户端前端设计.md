# SpringKB 前端界面设计 v2

**版本**：v2.1（2026-10-20，**视觉基调修订：档案馆 / 书房**）
**取代**：v2.0（暖橘 SaaS 视觉）与 v1.1（问答页单页设计稿）——本文件是**覆盖全前端（用户端 + 管理端）**的界面设计基线。
**设计基准**：本项目定位为**私有化单实例团队知识库**；视觉气质取自「档案馆 / 书房」，而非 SaaS 营销页。项目根目录 `demo.html` 仅作为**信息架构与组件清单**参考，其暖橘渐变视觉已于 v2.1 废止。
**关联文档**：[v2产品规划.md](./v2产品规划.md)、[详细设计_v2.md](./详细设计_v2.md)、[rebuild-frontend-v2/spec.md](../.trae/specs/rebuild-frontend-v2/spec.md)
**性质**：实现前需评审通过；**本变更不修改后端与业务逻辑**，冲突项见 §9。

## 1. 版本与范围

- **定位**：私有化单实例团队知识库 + RAG 问答。使用者是「在书房查资料的人」，不是「被营销转化的访客」。
- **v2.1 相对 v2.0 的修订**：**废止**暖橘渐变视觉（渐变主按钮、Hero 光斑、网格背景、逐张入场动画、大面积彩色投影）；改为**暖灰米白纸面 + 1px 暖灰 hairline 分层 + 深墨实底主操作 + 沉陶土极小面积强调**；问答页由「居中一张大卡片」改为**对话流**；管理端由「彩色工具风」改为**高密度中性控制台**。
- **覆盖范围**：
  - 用户端：首页 `/`、问答 `/qa`、知识库 `/kb`、文档详情 `/kb/doc/:id`、登录 `/login`、Setup 向导 `/setup`、个人中心 `/me`、写文档 `/editor`。
  - 管理端：`/admin` 及子路由（概览 / 文档管理 / 数据导入 / 成员管理 / 问答统计 / 知识盲区 / 待复审）。
- **交付节奏**：**先迁移并测试已实现功能**（问答、登录、管理端文档列表/导入/active 切换/删除/chunks），确认迁移成功后再进入 v2 新功能开发；迁移期间**保持前后端接口契约不变**（见 §8）。依赖未就绪后端的页面一律做**外壳（UI 骨架 + 空态）**，禁止 mock 伪造业务数据（见 §10）。

## 2. 视觉基调与设计原则

### 2.1 基调（一句话）

**档案馆 / 书房**：纸面、墨色、hairline、克制。信息靠**层级与留白**区分，不靠阴影与颜色。

### 2.2 原则

1. **单一视觉语言**：用户端与管理端共享字体 / 圆角 / 间距 / hairline；差异只在**底色**（用户端暖灰米白 `#F7F5F0`、管理端中性冷灰 `#F5F5F4`）与**信息密度**。
2. **分层靠 hairline，不靠阴影**：卡片与列表一律 `1px solid var(--hairline)`（`#E7E2D8`）；**禁用卡片/列表阴影**；阴影仅用于**下拉 / 弹窗 / 抽屉**等浮层，且极轻（`--shadow-overlay*`）。
3. **主操作 = 深墨实底**：`#1C1917` 实底、hover 微亮（`#292524`）；**禁用渐变按钮**。
4. **品牌强调 = 沉陶土 `#B45309`，极小面积**：仅用于导航活跃点、链接 hover、focus ring、数据高亮、管理端信号点。高饱和亮橘（`--brand-400 #F59E0B`）只允许出现在**单点高光时刻**（引用脉冲）。
5. **保留 Element Plus，不做替换**：EP 承担表单/表格/弹窗/消息等交互型组件，通过全局 CSS 变量与少量覆盖贴合基调（见 §3.2）；视觉型组件（导航、卡片、对话流等）用自定义组件还原。
6. **契约不变优先**：迁移阶段只消费现有接口，不改请求/响应结构。
7. **减量优先**：删除被取代的旧布局/旧视觉/旧路由，合并重复组件与样式。

### 2.3 字体与排版

- 中文：`PingFang SC` / `Source Han Sans SC`（思源黑体）/ `Noto Sans SC` 兜底；**不引入 webfont 依赖**，使用系统字体栈。
- 英文与**数字**：几何无衬线（`Inter` / `IBM Plex Sans` → `ui-sans-serif, system-ui`），数字一律开启 `font-variant-numeric: tabular-nums`（统计值、分数、版本号、表格数字列）。
- 标题字重 **600**（不用 800）；正文 `line-height: 1.7`。

### 2.4 动效

- **只出现在状态变化**：hover / 展开 / 切 tab / 提交中 / 结果到达。
- 时长 **200–300ms**（`--dur-fast 200ms` / `--dur-base 250ms` / `--dur-slow 300ms`），缓动 `cubic-bezier(.16,1,.3,1)`（`--ease-out`）。
- **禁止**：逐张入场动画（stagger）、常驻循环动画（唯一的例外是加载骨架的脉冲点与引用脉冲这一单次高光）。

### 2.5 禁止清单（硬性）

| # | 禁止项 |
| --- | --- |
| 1 | 渐变主按钮（`--grad-brand` 一类渐变底） |
| 2 | Hero 光斑 / 放射光晕（`--grad-hero`） |
| 3 | 网格 / 点阵背景纹理 |
| 4 | 逐张入场动画（列表 / 卡片 stagger） |
| 5 | 大面积彩色投影（卡片彩色 glow、hover 抬升彩色影） |
| 6 | 卡片 / 列表 `box-shadow`（含 hover 抬升） |

| `--el-box-shadow-light` | `var(--shadow-overlay-sm)` | 浮层 |

**覆盖之外需手工处理的三处**

1. **focus ring**：输入类控件 focus 时 `box-shadow: var(--ring)`（1px 陶土内描边），**不再派生自主色**；可聚焦控件 `:focus-visible { outline: 1px solid var(--brand-600); outline-offset: 2px; }`。
2. **表格**：`el-table` 关闭 `border`（无竖线）、无斑马纹（不用 `stripe`）、仅 `1px` 底部横向分隔线；分页器去按钮边框感、主色为墨色。
3. **禁用渐变**：删除一切 `background: var(--grad-*)`（含登录按钮、品牌方标、Hero）。

> 既有 `--grad-brand` / `--grad-soft` / `--grad-hero` / `--glow-brand` 与 `--shadow-xs..xl` 系列**随 v2.1 废止并删除**；卡片/列表不得再引用 shadow token。

## 4. 信息架构与路由表

### 4.1 导航结构

- **NavBar**（68px，吸顶）：底色 `rgba(247,245,240,.86)` + `backdrop-filter: blur(12px)` + **底部 1px `--hairline`**（无阴影）；左侧品牌为**深墨方标**（`--ink-900`）+ `Spring`/`KB` 两段文字（`KB` 用 `--brand-600`），**无渐变**。
- **主导航**仅三项：**首页 / 问答 / 知识库**；当前项以 `--brand-600` 圆点高亮（demo `.nav__link--active::after` 语义保留，颜色换为沉陶土）。
- **账户类入口**（右上头像菜单 UserMenu）：**个人中心 / 写文档 / 我的收藏 / 管理后台 / 退出登录**；用户名旁展示 `管理员` 徽标（`role` 归一化为大写后等于 `ADMIN` 才显示）；管理后台项带 `admin` 徽标且**不出现在主导航**。
- **未登录态**：右侧展示「登录」按钮（深墨描边文字按钮，非渐变实底）。
- **页面 Footer**：**仅首页 `/` 渲染** `AppFooter`；问答 / 知识库 / 文档详情 / 个人中心 / 写文档等功能页与管理端**不渲染**，避免过重的四列介绍占据功能页面底部。

## 8. 接口契约基线

### 9.1 C1 / C3 角色体系建议方案（本轮只记录，不改后端）

**现状缺陷（已实测）**：`AuthService.DEFAULT_ROLE = "ADMIN"`，任意人注册即成为管理员；`SecurityConfig` 对 `/api/admin/**` 只校验登录、不校验角色。因此「注册 → 自动管理员 → 可进管理后台并授予管理员」在 v1 是成立的。

**建议目标模型（最小可用版）**：

1. **首个用户 = 主管理员（bootstrap）**：注册时若 `kb_user` 表为空，则写入 `ADMIN`，即「首次部署的第一位注册者成为主管理员」；之后注册一律 `MEMBER`。
2. **角色变更只由管理员发起**：新增 `PATCH /api/admin/users/{id}/role`（仅 `ADMIN` 可调用），管理端「成员管理」页承载该动作；主管理员自身不可被降级（至少保留一名 `ADMIN`）。
3. **接口鉴权按角色收敛**：`/api/admin/**` 要求 `hasRole('ADMIN')`；`/api/qa/**`、`/api/kb/**` 仍按 `allow_anonymous` 决定。
4. **前端表现**：`UserMenu` 统一把后端 `role` 归一化为大写后判断，展示「管理员」徽标；非管理员不展示「管理后台」入口。

**本轮落地取舍**：只做**前端徽标归一化**（后端返回 `ADMIN` 大写，原判断 `=== 'admin'` 永不命中，已修正）；角色写入、鉴权与成员管理属后端变更，**按 C1/C3 记录，待裁决后单独实施**。理由：一旦注册默认改为 `MEMBER` 而 `/api/admin/**` 尚未做角色校验，会形成「普通成员仍可进管理端」的假安全，必须与鉴权改造同批发布。

## 10. 外壳占位与空态规范（v2.1 修订）

**空态文案规则（取代 v2.0 的「功能开发中 / 待后端就绪」）**：

> 每个空态 = **有态度的一句话（说明这是什么、为什么现在还是空的）** + **一个动作按钮**（可点的、有意义的下一步，而不是死路）。

- ✅ 示例：「这里还没有文档 —— 你先写一篇，团队的知识就从它开始」+ 按钮「去写文档」（若按钮对应能力也未就绪，则禁用并带 `title` 说明）。
- ✅ 示例：「还没有人问过问题 —— 第一个问题往往最有价值」+ 按钮「去问答」。
