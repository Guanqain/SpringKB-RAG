## P1 启动失败：ObjectMapper bean 缺失

- **遇到时间**：17:07
- **现象**：`mvnw spring-boot:run` 启动报 `required a bean of type 'ObjectMapper'`，应用无法启动。
- **根因**：Spring Boot 4.0.8 内置 **Jackson 3（`tools.jackson`）**，默认不再自动注册 Jackson 2（`com.fasterxml.jackson`）的 `ObjectMapper` bean。而 `SecurityConfig` 的 401 JSON 响应逻辑需要注入 ObjectMapper。
- **解决方案**：
  1. `pom.xml` 添加 `spring-boot-starter-json`（它是 Jackson 3 相关 bean 的唯一来源，**不可删除**）；
  2. `SecurityConfig` 改注入 `tools.jackson.databind.json.JsonMapper`，并使用其 `createObjectNode()` / `writeValueAsString()`。
- **经验教训**：Spring Boot 4 时代，凡是「找 ObjectMapper/JsonMapper bean」一律先确认是 Jackson 2 还是 Jackson 3 体系，别混用。

## P2 注册接口返回 401 但用户已入库

- **遇到时间**：17:14
- **现象**：`POST /api/auth/register` 返回 401 JSON，但数据库中用户已成功创建；前端表现为注册失败。
- **根因**：`UserRepository` 用 `KeyHolder.getKey()` 读取自增主键，PostgreSQL 在执行含 `RETURNING` 的插入时返回「多列结果集」，`getKey()` 抛 `InvalidDataAccessApiUsageException`；该异常在**未认证上下文**中冒泡，被 Spring Security 7 的 `ExceptionTranslationFilter` 统一转成 **401** 响应。
- **解决方案**：
  1. 改用 `INSERT ... RETURNING id` + `queryForObject(Long.class, ...)` 直接取 id，彻底绕开 `KeyHolder`；
  2. 排查此类问题时，把「接口报 401 但业务已生效」作为重要线索——先看后端日志有没有被 Security 吞掉的 Runtime 异常。
- **经验教训**：Spring Security 7 下，Controller 抛出的异常会被转成 401 而非 500，极易造成「登录状态失效」的误判。排查 401 时先查后端日志。

## P3 登录后自动弹回登录页

- **遇到时间**：17:35 前后（用户反馈）
- **现象**：登录成功进入后台，页面加载几秒后自动跳回 `/login?redirect=/`。
- **根因**：
  1. 前端 `DocumentList` 页挂载时调 `GET /api/admin/documents`，但后端**尚未实现** `/api/admin/*` 接口；
  2. 该路径不在放行白名单，无 handler 时 Spring Security 直接返回 401；
  3. 前端 axios 拦截器收到 401 → 清 token → 跳 `/login`，造成「登录被弹回」的假象。
- **解决方案**：
  1. 创建 `AdminController` 桩实现：`/documents` 返回空列表、`/documents/import`、`/documents/{id}/active`、`DELETE /documents/{id}` 均返回空结果；
  2. 带 token 实测 `GET /api/admin/documents` 返回 200，前端管理页可正常加载，不再弹回。
- **经验教训**：后端接口未实现前，必须提供 **stub** 保持链路完整；「登录后弹回登录页」大概率是某个未放行/未实现的接口触发 401，而非认证本身故障。

## P5 文档爬虫搭建 + kb_document 表结构数据驱动修订

- **时间**：19:00 ~ 19:30（约 30 min）
- **背景**：用户提出「先爬真实文档，依据实际元数据校验表结构」，避免拍脑袋设计不适配真实文档。
- **方案落地**：
  1. 新增 `crawler/` 包，按 **source adapter 模式**：`DocumentCrawler` 接口 + 每站一个实现；
  2. `RawDocument` 统一模型（source/product/version/language/docType/title/url/docKey/section/breadcrumb/lastModified/contentText）——字段超集，暴露真实站元数据；
  3. `CrawlerRunner` 入口：`--crawl=vue,springai,springboot`（或 all）触发，样本 JSON 落盘 `data/raw/*.json`（已 gitignore）。
- **成果**：三源各 80 篇样本全部产出——vue(720KB)、springai(1.09MB)、springboot(1.04MB)。
- **真实字段 vs 原设计差距**：
  | 真实数据 | 原设计 | 修订 |
  | --- | --- | --- |
  | 多产品共存（spring-boot/spring-ai/vue） | 无 product 维度 | 加 `product` |
  | vuejs 双语 zh/en | 无语言字段 | 加 `language` |
  | guide/api/tutorial/reference/howto | 无类型字段 | 加 `doc_type` |
  | spring 文档带 lastmod（增量更新） | 无 | 加 `last_modified` |
  | `source` 实为权威性，来源站点是另一维度 | 语义混淆 | 拆 `origin`（来源站点）+ `authority`（权威性） |
- **已同步**：`schema.sql`（kb_document 建表 + 唯一键 `(product, origin, authority, version, doc_key)`）、`详细设计.md` §4.3/§4.4、`agent.md`（D7/D8 决策）。
- **经验**：sitemap 是文档站的「目录」；动手前先抓一份看 URL 结构再写过滤规则，能省大量返工。

## P6 spring-boot sitemap 404 → 0 URL 两次修复

- **时间**：19:11 ~ 19:20（约 10 min）
- **现象 1**：`docs.spring.io/spring-boot/reference/sitemap.xml` 返回 **404**。
- **解决 1**：改用项目级 `docs.spring.io/spring-boot/sitemap.xml`（HEAD 200，但文件 13.6MB）。
- **现象 2**：项目级 sitemap 解析出 **0 个 URL**（`sitemap 共 0 个 URL`）。
- **根因**：新版 spring-boot 文档 URL 结构是 `https://docs.spring.io/spring-boot/<version>/reference/...` 与 `<version>/api/java/...`（javadoc），**不包含 `/reference/` 前缀**，被 `isDocPage` 的 `startsWith(BASE)` 过滤全部丢弃。
- **解决 2**：
  1. `BASE` 改为项目根 `https://docs.spring.io/spring-boot/`；
  2. 过滤只留含 `/reference/` 且 `.html` 结尾的页（排除 javadoc /api、index、images）；
  3. 版本号从 URL 提取（如 `4.2-SNAPSHOT`）——真实版本维度就此打通。
- **经验**：大站 sitemap 要先抽样看 URL 模式（本案例参考页 785 个，javadoc 上万个）；`spring-boot:run` 二次运行时遇到 `NoClassDefFoundError: RawDocument` 属增量编译脏类，`clean compile` 可解。

## P7 爬虫结构化重构：HTML → Markdown（标题层级/代码/表格/图片）

- **时间**：19:30 ~ 19:50（约 30 min）
- **问题（用户指出）**：原爬虫用 `Element.text()` 把正文压成扁平纯文本——丢失标题层级、代码块格式、表格结构；文档内图片未处理；导航/编辑链接噪声混入。
- **解决**：
  1. 新增 `HtmlToMarkdown`：Jsoup 逐节点遍历正文容器，按节点类型输出结构化 Markdown——`h1~h6`→`#` 层级（同时记录进 `headings` 分块锚点）、`pre/code`→围栏代码块（识别 `language-*` 语言）、`table`→Markdown 表格、`img`→`![alt](src)`（同时记录进 `images`）、列表/引用/链接保留；`script/style/nav/header/footer/aside/form` 等噪声直接跳过。
  2. `RawDocument` 升级：新增 `contentMarkdown`（结构保留，供分块）、`images`（src+alt，供后续下载/OCR/多模态）、`headings`（level+text+anchorId，供按标题分块）。
  3. 三个源适配器统一接入；`contentText` 保留为纯文本（Embedding 用）。
- **验证**：Vue 源 80 篇重爬（1.5MB）。抽查 guide 页：headings 25 个层级完整（h1~h4）、图片 5 张 alt+src 提取、代码围栏与表格均转换成功。
- **待办/发现**：
  - vuejs.org 页面顶部有「Are you an LLM?…」提示噪声，需剔除；
  - vuejs 站提供 `.md` 端点（LLM 优化版），后续可直连，比 HTML→MD 更干净；
  - 图片本体未下载（样本阶段只记录引用；导入阶段再落本地/对象存储）。
- **经验**：生产级爬虫的核心是「结构保留」而非「文本抽取」；标题层级是后续分块与 RAG 召回质量的地基。
