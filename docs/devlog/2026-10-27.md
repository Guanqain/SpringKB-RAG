## 七、经验教训

1. **链路层面的 reset 只能靠重试次数解决**：改 UA / 改连接头无效时，先量化「单次成功率」，再按 `1-(1-p)^n` 选重试次数；同时把重试做成站点级可配置，不要全局调高（会拖慢其它源）。
2. **进度与状态必须落盘，不能只依赖日志输出**：日志会被重定向破坏编码、也会被进程独占；状态文件 + 增量文件才是可靠事实源。
3. **「进程在」不等于「任务在跑」**：判断爬虫是否结束要看断点文件是否增长、日志时间戳与 CPU 增量。
4. **幂等跳过是正常现象，不是失败**：重跑全量导入时旧源 100% 跳过（1512 篇），看 `skipped` 要区分「已存在」与「空正文」。
5. **chunk 大小要按语言估算 token**：`字符数/4` 只适用于英文；中文语料应按「CJK 字符 ≈ 1 token」估算，否则会撞 Embedding 输入上限。

## 九、CJK token 估算与超长块兜底修复（当日追加）

**问题**：mysql `mysqlbinlog` / `gpg-key-archived-packages` 导入报 `Tokens in a single document exceeds the maximum number of allowed input tokens`。Spring AI 的 `TokenCountBatchingStrategy` 用 CL100K 统计，上限 8191、预留 10%（约 **7371**），单条 Document 超限即抛异常。

**根因（两处叠加）**：

1. `TokenEstimator.estimate` 统一按 `字符数/4`：中文约 1 字 ≈ 1 token，被低估约 4 倍；
2. `hardSplit` 对代码围栏内的行不做预算检查，一个 2.6 万字符的代码块会整体落成一个 chunk（估 6660 token，CL100K 实测已超 7371）。

**修复**：

| 位置 | 改动 |
| --- | --- |
| `TokenEstimator` | 按字符权重累加：CJK（汉字/假名/谚文/全角）1 token/字符，其余 4 字符/token；新增未取整的 `weightSum` 供逐行预算使用 |
| `ChunkSplitter.hardSplit` | 逐行用 `weightSum + 换行权重` 计预算（避免大量短代码行因逐行取整而系统性低估约 25%）；围栏块上限 **2×maxTokens**，超限时「补闭合围栏 → 以同语言标记重开」，每块围栏仍成对 |
| `ChunkSplitter.splitLongLine` | 超长单行改为按 token 预算切分（原按 `maxTokens*4` 字符切，中文会切不动） |
| `ChunkSplitter.pack` | 增加单块硬上限 2×maxTokens 的 flush 条件 |

**验证**：

- 实测两篇失败文档（用 CL100K 直接数 token）：`mysqlbinlog` 10 chunk / maxEst 1987 / **maxReal 1932**；`gpg-key-archived-packages` 8 chunk / maxEst 1993 / **maxReal 5761**，全部 < 7371；
- 重导 `--import=mysql`：2346 篇 → **ok=2 / skip=2344 / fail=0**（耗时 8s），两篇均已入库，`kb_chunk` 与 `vector_store` 各 10 / 8 条对齐，`token_count` max 1987 / 1993；
- 单测新增 4 例（CJK 估算 / 中文长节 / 超大围栏成对切分 / 无换行中文长行），全量 `mvn test` **138/138** 通过。

## 十、docId 规范化碰撞修复（当日追加）

**问题**：python 源 `genindex-_` 导入报 `DuplicateKeyException`（主键 `kb_document_pkey`）。

**根因**：`buildDocId = {product}-{version}-{规范化 docKey}`，规范化会把 `_` 等非法字符替换成 `-` 再压缩，导致 `genindex` 与 `genindex-_` 都变成 `python-3-genindex`；而幂等检查用的是**原始** `doc_key`，两篇不同原文都能通过检查，第二篇必然撞主键。

**修复**（`IngestionService`）：

| 位置 | 改动 |
| --- | --- |
| `importDocument` | 幂等检查后改用 `resolveDocId(doc)` 计算最终 id |
| `resolveDocId` | 若规范化 id 已被「docKey 不同」的文档占用，改用 `{规范化id}-{SHA-256(docKey) 前 10 位}`；再碰撞则追加 `-2..-10`，仍失败才抛异常 |
| `takenByOther` | `SELECT doc_key FROM kb_document WHERE id = ?`，同 docKey 视为幂等命中，不同才判定碰撞 |
| `shortHash` | SHA-256 前 10 位十六进制，稳定可复现（不用 `String.hashCode`，避免 32 位碰撞与跨实现差异） |

**关键取舍**：只对**真正碰撞**的文档追加后缀，已有 1.1 万条数据的 id 全部保持不变（若改成「永远带 hash」需要全量重导）。

**验证**：

- 重导 `--import=python`：734 篇 → **ok=1 / skip=733 / fail=0**（5s）；`genindex-_` 落到 `python-3-genindex-c69b8d5c52`（6 chunk / 6 向量），`genindex` 仍是 `python-3-genindex`，两篇并存；
- 幂等：再导 `genindex-_` 为 SKIPPED（按原始 doc_key 命中，哈希后缀不会造成重复入库）；
- 单测新增 2 例（规范化碰撞自动哈希、`shortHash` 稳定性/长度），`IngestionServiceTest` 7/7、全量 `mvn test` **140/140** 通过；
- 库内计数：11105 文档 / 29206 chunk / 29208 向量。

- `.\mvnw.cmd test`：27 个测试类、**141 例全部通过**（`AdminApiTest` 适配分页返回，并新增 stats 聚合用例，期望值实时查库比对）；

**经验教训**：

1. **「可选分页」等于没有分页**：只要接口保留了全量分支，前端迟早会走那条路；列表接口默认就应该分页。
2. **统计不要在前端做**：`reduce` 一个万级数组和一条 `GROUP BY` 的成本差两个数量级，且前者把 IO 从 DB 搬到了网络 + 浏览器。

4. **分页 + 筛选要重置页码**：筛选变更后仍停在第 7 页会看到空列表，必须回第 1 页。

**经验**：要让两栏独立滚动，必须同时给**父容器固定高度**和**子容器 `min-height: 0`**；只写 `overflow: auto` 时 flex/grid 子项默认 `min-height: auto`，会被内容撑高，滚动条依旧落在整页上。

## 十三、管理后台概览页重设计：全系统状态看板

**背景与问题**：原概览页（`frontend/src/views/admin/AdminOverview.vue`）是「文档管理页的缩略版」——几张文档计数卡 + 技术分布 / 来源分布，数据来自 `GET /api/admin/stats` 的一条 `GROUP BY ROLLUP(product)`。它答不了管理员真正关心的问题：

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 只有文档静态存量（总数 / 启用 / 待审 / chunk / official / community） | 看不到「最近新增」「最近问答」「最近拦截」等时间维度 |
| 2 | 没有任何环比 | 数字涨跌无法判断是正常波动还是异常 |
| 3 | 待办散落在审核 / 通知 / 导入 / 脱敏各页 | 管理员要逐个菜单点进去才知道今天该做什么 |
| 4 | 没有口径说明 | 「活跃用户」「命中率」这类指标人各一解，数字无法对齐 |
| 5 | 图表若引入全家桶（ECharts） | 主 chunk 体积失控 |

结论：概览页应重做成**全系统状态看板**——首屏先回答「今天要做什么」，再回答「系统在各维度怎么样」。

**接口变更（BREAKING）**：

| 项 | 变更 |
| --- | --- |
| 删除 | `GET /api/admin/stats`（`manage/AdminController`）与 `dto/AdminStats.java` |
| 新增 | `GET /api/admin/overview?days=7\|30`，仅 `hasRole('ADMIN')`；`days` 缺失 / 非 7 / 非 30 一律**钳制为 7** |
| 新增 | `dto/AdminOverview.java`：嵌套 record `Cards` / `Sections { ContentStats, GovernanceStats, QaStats, UserStats, EngagementStats, HealthStats }` / `TrendSeries` / `TodoSummary` / `Meta` |
| 影响 | 前端 `api/document.ts#fetchAdminStats` 与 `types/document.ts#AdminStats` 随旧接口移除，`AdminOverview.vue` 整体重写；无其他调用方 |

**五域指标与口径**：窗口统一为「近 N 天」（`days=7|30`），环比基线为**上一个等长窗口**（即 N~2N 天前），全部数字由单条聚合或 JOIN SQL 算出。

| 域 | 指标来源 | 时间窗与环比 |
| --- | --- | --- |
| 内容 Content | `kb_document`（总量 / 新增 / 待审） | 新增按 `created_at` 落窗；环比 `content.prevWindowNewDocs` |
| 治理 Governance | `kb_document.review_status` + `kb_scan_log` 拦截 | 按 `reviewed_at` / `created_at` 落窗；环比 `scan.prevWindowBlocks` |
| 问答 QA | `kb_message`（提问与回答） | 按 `created_at` 落窗；环比 `qa.prevWindowQa` |
| 用户 User | `kb_user` 注册 + 窗内活跃（问答 / 点赞 / 收藏） | 按 `created_at` 落窗；环比 `users.prevNewInWindow`、`users.prevActiveInWindow` |
| 互动 Engagement | `kb_doc_like` / `kb_doc_favorite` 行为表 | 按行为创建时间落窗 |
| 系统健康 Health | chunk / 向量覆盖、异常规则、导入状态等 | 存量口径，不参与环比；面板横跨两列 |

**8 条设计约束的落地方式**：

| # | 约束 | 落地 |
| --- | --- | --- |
| 1 | 每个面板都要有口径说明 | `AdminOverview.vue` 的 `METRIC_HINTS` 常量写清分子 / 分母 / 时间窗，面板标题旁渲染「?」角标（`el-tooltip`） |
| 2 | 窗口指标显示环比 | 「较上一周期 ▲/▼ N%」；上期基线为 0 时显示「—」，不出现 `∞%` |
| 3 | 待办条位于首屏第一行 | 工具栏之后立即渲染 4 项待办，先于 8 张核心卡 |
| 4 | 无聚合缓存 + 仅补 `created_at` 索引 | 全部单条聚合 / JOIN SQL，无 `@Cacheable` / Redis / 本地缓存；索引只加 3 个 `created_at` |
| 5 | 图表依赖只允许按需注册 | 手动 `Chart.register(...)` 注册所需元素与 Controller，无 `chart.js/auto`、无 ECharts |
| 6 | 盲区与脱敏统计的去标识化 | 盲区只显示**问题原文截断 60 字**、不含用户名；拦截只显示**规则类型 / 数量 / 动作** |
| 7 | 图表 props 只吃归一化数据 | 分布类 `{label,count,pct}[]`、趋势类 `{date,newDocs,qaCount}[]`，组件内不做业务计算 |
| 8 | 视觉与无障碍双保险 | 同色系明度差 + 数值文字双编码；`role="img"` / `aria-label` / `sr-only` 文本 |

**图表选型与体积**：

| 项 | 值 |
| --- | --- |
| 图表库 | Chart.js 4，按需注册 `ArcElement` / `BarElement` / `LineElement` / `PointElement` + `CategoryScale` / `LinearScale` + `Tooltip` / `Legend` + 三个 Controller |
| 明确禁止 | `chart.js/auto`（会把整包拉进主 chunk）、ECharts（体积不可接受） |
| 新增组件 | `components/admin/charts/theme.ts`（配色 / 字体）、`DonutChart.vue`、`BarList.vue`、`TrendChart.vue`、`SplitBar.vue`（纯 CSS，不占 canvas） |
| 体积 | 改动前主 chunk gzip **438.06 KB**；改动后 `index-CsN2gVoe.js` 1544.46 KB / gzip **514.57 KB**，增量 **≈76.51 KB**，满足 ≤80 KB 预算 |

**索引与 EXPLAIN 结论**：`schema.sql` 新增 `idx_kb_document_created_at (created_at)`、`idx_kb_message_created_at (created_at)`、`idx_kb_user_created (created_at)`。dev 库 `kb_document` 共 11106 篇且**全部落在窗口内**，`created_at >= now()-N days` 选择率接近 100%，planner 按代价模型默认选择 **Seq Scan**——这是合理选择，**不是索引缺失**。对照验证：`SET enable_seqscan=off` 后同一查询改走 `idx_kb_document_created_at`，且为 **Index Only Scan**。

**隐私边界**：

- 盲区排行只输出**问题原文截断 60 字**，不附带用户名 / 邮箱 / open_id；
- 脱敏拦截统计只输出**规则类型 / 命中数量 / 操作动作**，绝不展示命中明文（延续 `kb_scan_log` 不落正文的约定，坑 #61）。

**验证结果**：

| 项 | 结果 |
| --- | --- |
| 后端单测 | `.\mvnw.cmd test` → **146 tests / 0 failures** |
| 前端静态检查 | `npm run check` 通过 |
| 前端构建 | `npm run build` 通过；主 chunk gzip 514.57 KB（+≈76.51 KB，≤80 KB） |
| 浏览器实测 | **未执行**：当前环境缺少管理员登录态，访问 `/admin` 会被重定向到 `/login`，本轮未做页面级回归；图表渲染、7/30 切换、刷新时间戳、待办条跳转**待人工登录后确认** |

**经验**：

1. **看板先答「该做什么」，再答「怎么样」**：待办条放在核心指标之前，管理员打开页面第一眼就有行动项。
2. **环比必须有基线**：没有「上一等长窗口」的数字，百分比只是噪声；基线为 0 时显示「—」而不是无穷大。
3. **聚合不进缓存**：万级数据下单条聚合足够快，缓存带来的失效问题远大于收益；先补 `created_at` 索引，再看 EXPLAIN。
4. **「走 Seq Scan」不等于索引失效**：当窗口覆盖全表时 Seq Scan 是最优解，用 `enable_seqscan=off` 对照才能区分「planner 合理选择」与「索引缺失」。
5. **图表体积要按需注册**：`chart.js/auto` 一行带来的是整包；按需 `Chart.register` 才能把增量压在预算内，纯 CSS 图形优先。
