# 续 · 问答引用相关性修复

> **主题**：检索结果不相关时仍返回引用
> **状态**：✅ 完成，`QaServiceTest` 9/9 通过

## 现象

用户提问后答案明显与知识库内容无关（或模型自己都说「知识库中未找到相关答案」），前端却仍然渲染出一排来源卡。

## 根因（三层，缺一不可）

1. **`found` 只看首条分数**：`ask` 只用初检第一名的 `topScore` 与阈值比较；只要第 1 条勉强过线，后续 4 条弱相关 chunk 也一并放行。
2. **引用未做分数过滤**：`resolveSources(reranked)` 把重排后的 topK **全部**聚合成 `SourceRef`，没有任何 `score ≥ threshold` 判断。
3. **模型兜底话术未被识别**：prompt 要求「不足以回答时明确回答『知识库中未找到相关答案』」，但 `generate` 返回后仍直接 `new QaResult(true, answer, sources)`——模型判了无答案，外层还是 `found=true` + 引用。

## 修复

- `resolveSources(reranked, similarityThreshold)`：文档级聚合后 `maxScore < minScore` 的分组直接跳过；角标在过滤后重新连续编号（仍是 1..n）。
- `ask`：`generate` 返回 `null` 或包含 `NO_ANSWER` 时统一返回 `new QaResult(false, NO_ANSWER, List.of())`，不再展示无意义引用。
- prompt 规则 4 补充「包括检索内容与问题主题无关、仅字面相似」的情形，并把指令改为「只回答该句，不要引用任何内容」。
- **阈值保持 `0.5` 不放回 0.65**：双语检索验收依赖 0.5（`如何配置 CDS` topScore 0.5696），提高阈值会误杀已验证命中；引用相关性改由「来源级分数过滤 + 模型兜底识别」保证。

## 测试

`QaServiceTest` 新增 2 例：

- `weakSourcesAreFilteredOut`：强文档（cos≈0.94）+ 正交弱文档（cos≈0），`sources` 只含强文档且角标为 1。
- `modelNoAnswerDropsSources`：模型返回 `NO_ANSWER` → `found=false`、`sources` 为空。

日志可见「重排后=2 条，回源且达标=1 条」，与预期一致。

## 复盘要点

- **兜底判定不能只做一次**：入口分数（topScore）与出口来源（每个 SourceRef）是两个不同粒度，前者过线不代表后者都相关。
- **模型自带兜底话术必须回收**：既然 prompt 允许模型说「未找到」，就必须把这句话当作信号处理，否则 prompt 与后处理逻辑各说各话。

## 经验教训

1. **`OLLAMA_MODELS` 只对「新启动的进程」生效**：本次开机后 Ollama 托盘程序已自行启动，其模型目录仍是默认的 `~/.ollama/models`，`ollama list` 显示为空（D 盘明明有 639 MB 的模型），若此时直接跑导入，会重新往 C 盘下载。**先 `Stop-Process -Name 'ollama app','ollama'`，再以带 `OLLAMA_MODELS=D:\ollama\models` 的 shell 启动 `ollama serve`，`ollama list` 能看到模型后再继续**。
2. **重算向量必须先清 `vector_store`**：`--import=all` 走 `kb_document` 幂等判断（同 product/origin/authority/version/doc_key 即跳过），不清表只会「全部 skip」，向量不会重算。
3. **停掉 compose 里的 `rag-app`**：`docker compose up -d` 会连带启动预构建应用容器并占用 8080、连同一个库，手工导入期间应只保留 `rag-postgres`。

# 续 · 写文档异常登出 + 后台技术分布修复

> **主题**：写文档页被异常踢回登录、管理端技术分布无法甄别技术类型
> **状态**：✅ 完成，`mvn clean test` 93/93、`npm run build` 通过、浏览器三项验收全过

## 现象

1. 在 `/editor` 写文档（发布或上传）时会**异常退出登录**，被弹回 `/login`；同一时间问答、知识库也偶发同样的「踢出」。
2. 管理端 `/admin` 概览的「技术分布」**无法甄别技术类型**——所有文档都落到「未分类」，或只剩某一个分类。

## 根因（四层叠加）

| # | 层 | 问题 |
| --- | --- | --- |
| 1 | 运行时 | 8080 上跑的是**旧编译产物**。`AdminService.categories` 源码里 `rs -> names.put(...)` 是表达式体 lambda，同时满足 `ResultSetExtractor<String>`（有返回值）与 `RowCallbackHandler`（表达式语句与 void 兼容），属**重载歧义**；`target/classes` 里存在 IDE/ECJ 容错产出的 `Error` 桩类，运行时抛 `java.lang.Error: Unresolved compilation problem`，被 Spring Security 转成 **401** → 前端 axios 见 401 即清 token 跳登录 |
| 2 | 接口语义 | 匿名调用 `GET /api/auth/me` 时，`/api/auth/**` 是 permitAll，Security 注入 `AnonymousAuthenticationToken`（`isAuthenticated()` 恒 true），旧逻辑以 `anonymousUser` 查库返回 **业务码 400「用户不存在」**，前端无法识别为登录失效 |
| 3 | 前端登录态 | `stores/auth.ts#restoreSession` 对**任何异常**都 `clearAuth()`：网络抖动 / 后端 5xx 也会把用户登出 |
| 4 | 前端统计 | `AdminOverview.vue` 复用 `useDocumentStore()`（全局单例），沿用文档管理页留下的 `store.filter` → 从「文档管理」带筛选回概览时技术分布只剩被筛中的分类 |

## 修复

- **后端 `manage/AdminService.categories`**：`query` 的 lambda 改**块体**（`rs -> { ... }`），消除重载歧义；并在 `mvn clean` 后重建，清掉错误桩类。
- **后端 `controller/AuthController.me`**：改用 `CurrentUser.username(authentication)` 判登录，匿名/无效 token 返回业务码 **401**（HTTP 仍 200），只有已登录才查库。
- **前端 `api/http.ts`**：业务非 0 时把 `code` 挂到抛出的 Error 上，供调用方区分「登录态失效 401」与普通业务错误 400。
- **前端 `stores/auth.ts`**：`restoreSession` 只在 `response.status === 401` 或业务 `code === 401` 时 `clearAuth()`；网络中断 / 5xx 保留 token。
- **前端 `views/admin/AdminOverview.vue`**：改为页面内独立 `listDocuments()` 全量拉取（不碰 `store.filter`），技术名取 `kb_category.display_name`（回落 `product`），根节点加 `v-loading`。

## 测试与验证

- `mvn -q clean test`：**93 例全通过**（18 个测试类，Failures 0 / Errors 0）。新增 `AuthApiTest#meReturns401CodeWhenAnonymousOrTokenInvalid`（匿名与无效 token 均 `code=401`，登录后返回本人）。

## 经验教训

1. **`mvn test` 通过 ≠ 跑着的进程是新代码**：遇到「莫名 401 / 莫名异常」先核对 8080 进程启动时间与 `target/classes` 时间戳，再看后端日志尾部有没有 `Unresolved compilation problem`（它只在请求时报，启动日志看不到）。修完代码要 `mvn clean`，别让增量编译复用旧桩类。
2. **`JdbcTemplate.query(String, lambda)` 优先写块体**：表达式体 `rs -> map.put(k, v)` 会在 `ResultSetExtractor` 与 `RowCallbackHandler` 之间产生歧义；要返回值就用双参 `RowMapper`。
3. **permitAll 路径上的「当前用户」不能用 `isAuthenticated()` 判**：匿名 token 恒为 true，必须用 `CurrentUser.username()` 拿用户名再判 null。
4. **「清登录态」是最高危操作**：只允许对明确的 401 生效，其余异常一律保留 token，否则弱网下用户体验就是「被随机登出」。
5. **管理端各页共享 Pinia store 时，统计页必须自取全量**：筛选条件是页面级状态，不该泄漏进概览。

# 续 · 邮箱验证码真实投递（SMTP）

> **主题**：验证码此前只写日志 / 靠 devCode 回显，并未真正发邮件
> **状态**：✅ 实现完成，`mvn clean test` 95/95 通过

## 现象

用户反馈「发送邮箱验证功能并没有真正实现」：点「发送验证码」后收不到邮件，验证码只出现在服务端日志里，本地能注册成功是因为接口回显了 `devCode`。

## 根因

`EmailCodeService.send` 只做「生成码 → 入库 → 打日志」，工程**没有引入任何邮件依赖**，也没有 SMTP 配置，`devCode` 回显掩盖了「未投递」的事实。

## 修复

- `pom.xml` 引入 `spring-boot-starter-mail`（Boot 4.0.8 对应 `spring-boot-mail` 自动配置模块）。
- 新增 `config/MailConfig`：`app.mail.enabled=true` 时才创建 `JavaMailSenderImpl`（`@ConditionalOnProperty`），host/port/username/password/from/ssl 全部来自 `MAIL_*` 环境变量；显式设置 SMTP `connectiontimeout/timeout/writetimeout=5s`（否则 SMTP 不可达会挂死请求线程，与坑 #32 同类）。
- `EmailCodeService`：注入 `ObjectProvider<JavaMailSender>`（可选依赖），插入验证码后调用 `deliver()` 真实发信；未配置 SMTP 时 WARN 日志回落；发送失败**删除刚写入的码**并抛 `IllegalArgumentException("验证码邮件发送失败，请稍后重试")`，避免 60 秒冷却把用户挡在门外。`INSERT ... RETURNING id` 取回主键用于失败回滚。
- `application.yml` 新增 `app.mail.*`（默认 enabled=false，`from` 缺省回落到 username）；`application-dev.yml` 注释说明本地默认仍走 devCode 回显。

## 配置方式（真实收信）

```bash
# QQ 邮箱示例（password 填「授权码」，不是登录密码）
MAIL_ENABLED=true
MAIL_HOST=smtp.qq.com
MAIL_PORT=465
MAIL_SSL=true
MAIL_USERNAME=your@qq.com
MAIL_PASSWORD=<SMTP 授权码>
MAIL_FROM=your@qq.com
```

生产同时把 `APP_AUTH_CODE_ECHO` 保持 false（默认值），验证码只出现在邮件里。

- 新增 `EmailCodeMailTest` 2 例（独立 properties 建上下文 + `@MockitoBean JavaMailSender`，不连真实 SMTP）：
  - 开启邮件后 `send(MimeMessage)` 被调用，收件人/主题「注册验证码」/正文包含 devCode；
  - 发送抛 `MailSendException` 时返回业务码 400「验证码邮件发送失败，请稍后重试」，且该邮箱验证码记录被删除（冷却不锁死）。

## 经验教训

1. **「能用」的假象常来自回显/日志**：本地 `devCode` 回显让「没投递」看起来正常，验收时要问「用户真的收到邮件了吗」。
2. **可选基础设施一律用 `ObjectProvider` 注入**：SMTP 属于「有配置才启用」的 bean，直接构造器注入 `JavaMailSender` 会在未配置时启动失败。
3. **出站调用必须设超时**：SMTP 与 HTTP 一样，默认无限等待；连接/读/写各 5s，失败快速反馈。
4. **失败要可重试**：先写库再发信时，发送失败必须回删记录，否则冷却机制会阻止用户立刻重试。

## 真实投递验证（19:14 / 19:16）

- 以 QQ 邮箱 SMTP（`smtp.qq.com:465`，SSL）启动后端，`POST /api/auth/email-code` 返回 `code=0`，日志出现「验证码邮件已发送」，邮箱实际收到「注册验证码」与「登录验证码」两封邮件。
- 以 `APP_AUTH_CODE_ECHO=false` 启动时响应 `devCode=null`，证明验证码只走邮件、不再回显（`application-dev.yml` 已改为 `${APP_AUTH_CODE_ECHO:true}`，可被环境变量覆盖）。
- SMTP 凭据仅通过进程环境变量注入（`MAIL_*`），未写入任何被 Git 跟踪的文件；长期使用建议配置到 IDEA Run Configuration 的环境变量或系统环境变量中。
- 同一邮箱 60 秒冷却在真实验证中生效（第二次请求返回「验证码已发送，请 60 秒后重试」），与设计一致。

# 续 · 登录方式合并 + 未注册邮箱引导建号

> **主题**：密码登录 / 验证码登录不该是两个并列分类；验证码登录遇到未注册邮箱应引导建号而不是报错

## 现象与诉求

1. 登录页把「登录 / 注册 / 验证码登录」做成三个并列 tab，密码登录与验证码登录本质都是登录，应该在一个入口里切换。
2. 用未注册邮箱走验证码登录时报「该邮箱未绑定账号」，把用户挡在门外；正确做法是验证通过后引导补充用户名 + 密码，直接建号并登录。

## 后端改动

- `EmailCodeService` 拆分：`check()` 只校验不消费（返回验证码记录 id），`consume(id)` 消费，`verify()` = check + consume。原因：未注册邮箱场景要「先证明邮箱归属、建号成功后再消费验证码」。
- `AuthService.loginByCode` 改为返回 `CodeLoginResult`：
  - 先校验验证码（**不消费**）再查库——验证通过前不暴露「邮箱是否已注册」，避免账号枚举；
  - 已注册 → 消费验证码并返回 `action=login` + token/user；
  - 未注册 → 返回 `action=needs_profile` + email，验证码保留（5 分钟内可继续完成建号）。
- 新增 `POST /api/auth/register/email`（`EmailRegisterRequest`：email / code / username / password）：复验 login 验证码 → 检查邮箱与用户名占用 → 消费验证码 → 建号并签发 JWT（首用户仍是 ADMIN）。

## 前端改动

- `Login.vue`：tab 收敛为「登录 / 注册」；登录内用 `el-radio-group` 分段按钮切换「密码登录 / 验证码登录」；字段显隐、校验规则、提交字段都随模式计算。
- 验证码登录返回 `needs_profile` 时：显示「该邮箱还没有账户」引导卡片（展示已验证邮箱），展示用户名 + 设置密码输入框，主按钮变「创建账户并登录」，并提供「返回验证码登录」；此时**不写登录态**，避免半登录状态。
- `types/auth.ts` 新增 `CodeLoginResult`；`api/auth.ts` 新增 `registerByEmail`；`stores/auth.ts` 的 `loginByCode` 仅在 `action=login` 时 `setAuth` 并返回结果，新增 `registerByEmail`。

## 测试与验收

- 新增 `AuthApiTest#codeLoginForUnregisteredEmailGuidesToCreateAccount`：未注册邮箱验证码登录返回 `needs_profile` 且不消费码 → `register/email` 建号返回 token/user → 同一验证码不能复用（400）。
- `mvn -q clean test`：**96/96 通过**（21 个测试类）；`npm run build` 通过。
- 浏览器验收（5173）：仅「登录 / 注册」两个 tab；登录内「密码登录 | 验证码登录」可切换且字段随之变化；未注册邮箱 → 出现引导卡片、无红色报错；补全用户名密码 → 直接登录并跳首页；控制台无报错，请求全部 2xx。验收账号与验证码记录已清理。

## 经验教训

1. **登录方式属于同一业务的「模式」而非「分类」**：tab 用于业务入口（登录/注册），模式切换用分段控件，信息层级才对。
2. **验证码消费时机要跟着业务结果走**：先消费后建号会让用户在建号失败时无法重试；拆成 check/consume 后，只有真正完成登录/建号才置 `used`。
3. **防枚举顺序**：必须先校验验证码再判断「邮箱是否存在」，否则接口会变成注册状态查询器。

## 本轮踩坑与修复

1. **docs.docker.com TLS 握手失败**（`Remote host terminated the handshake`，curl 加 `--insecure` 才能通）：`AbstractSitemapCrawler` 增加 `connection(url)` 钩子，`DockerDocsCrawler` 覆盖并注入 trust-all `SSLSocketFactory`；并伴随偶发 `Connection reset`。

7. **Node.js 中文站是 SPA**：`nodejs.org/zh-cn/api` 由前端渲染，静态抓取拿不到正文，改用官方英文 `nodejs.org/api/`。

## 经验教训

1. **审核状态不要复用 `active`**：`active` 表达「是否在库」，审核表达「是否允许公开」，两个维度混用会让「待审文档在管理端不可见/不可操作」；独立列 + 独立过滤表达式最省事，且历史数据用列默认值零迁移。

5. **驳回重提走「删旧建新」**：chunk / 向量 id 与 docKey 绑定，原地重建会留下孤儿向量；删干净后用新随机 docKey 重新导入，幂等与可观测性都更好。
6. **未注册邮箱的找回密码要「等长响应」**：TTL / 冷却 / devCode 三项与已注册一致且不发码，否则接口会变成账号状态查询器。

## 经验教训

1. **规则播种用 `ApplicationRunner` 而非 `@PostConstruct`**：`@PostConstruct` 可能早于 `schema.sql` 建表，遇到「表不存在」不要怀疑 SQL 写错，先看初始化顺序。
2. **播种必须「不覆盖」**：`ON CONFLICT DO NOTHING` 保证升级重启不会把管理员关掉的规则重新打开。
3. **审计与业务事务必须分开**：发布命中会抛异常回滚，审计若同事务就一起消失；`REQUIRES_NEW` 是「留痕」这类旁路写的标准做法。
4. **通知与审核同事务**：审核失败不留通知、审核成功必有通知，避免「状态改了但作者没收到消息」。
5. **批量操作用「逐条 + 收集错误」而不是「一条失败全回滚」**：审核队列里部分文档已被人处理是常态，返回 `{approved, failed, errors}` 比整批失败更可用。
6. **可配置规则要保留纯函数入口**：`SensitiveScanService.scan(content)` 保留内置规则语义，既有单测不用改；DB 规则走 `scan(content, rules)`，职责清楚、回归面小。
