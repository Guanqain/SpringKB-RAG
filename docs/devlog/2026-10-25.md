> **产出**：[docs/检索基线测评报告.md](../检索基线测评报告.md) ｜ `data/baseline/result-20261025-144622.json`

## 背景与目标

为 RAG 系统的**检索阶段**（不含生成）建立一份可信的基线数据，作为后续调参（阈值双条件改造、boost 权重、chunk 策略）的对照基准。可信 = 指标口径可复现（固定种子 + 真实语料 + 真实 Embedding）+ 与既有单点验证一致。

## 方案要点

1. **评测集（ground truth）混合构建**：
   - **合成自检索 ~120 条**：对语料按 `product × authority × version` 分层抽样（seed=42），用「标题 + 末段 heading + 首块前 20 词」构造查询，其目标文档即该抽样文档（doc 级单相关）。用于测「按文档找回自己」的能力上界。
   - **精选真实问句 25 条**：`resources/eval/queries.json` 金标集，覆盖 spring-boot/spring-security/spring-framework/spring-ai/spring-data-jpa/vue/vue-router/vite/pinia/community/negative，含 2 条负例（`relevantTitles` 为空）。用于贴近真实用户问法。
2. **运行载体**：`eval/BaselineRunner`（`ApplicationRunner`，`--baseline` 激活）复用线上 `RagSearchService#searchDocuments`（初检）+ `Reranker#rerankAndTop`（重排），与生产同一条代码路径。
3. **指标四维**：标准 IR（Hit@K / Recall@K / Precision@K / MRR / nDCG）+ 版本过滤正确性（targetHit / leakRate / correctness）+ 兜底行为（rate / topScore 分布 / 负例正确率）+ 权威重排效果（official 平均名次提升 / 提升占比）。
4. **口径锁定**：`BaselineEvaluator` 为纯函数指标器，`BaselineEvaluatorTest` 8 例单测锁定各指标计算公式，避免「实现漂移」。

## 结果可信性核验

1. **版本过滤**：120 条锁定版本查询 leakRate = 0，与既有单测（下推证明）及测试用例文档「双向无跨版本泄漏」一致。
2. **兜底**：可答查询 topScore 最小 0.5134 > 阈值 0.5，故兜底率 0（无漏杀）；2 条负例全部正确兜底（无漏放）。
3. **权威重排**：official 平均名次提升 +1.03 为正，方向符合 `+0.15 boost` 语义；提升占比 0.118 较低 → 印证「boost 是微调非覆盖」（与测试用例文档§3 边界记录一致）。
4. **合成 vs 精选落差**：合成 Hit@10 0.9167 > 精选 0.8696，符合「自检索高估、真实问法更贴近上界」的预期（报告 §3 已标注该偏差）。

## 经验教训

1. **评测集决定结论可信度**：纯合成「找自己」会高估，必须在报告里显式区分「能力上界（合成）」与「真实读值（精选）」，否则基线会误导后续调参判断。
2. **指标口径要用单测锁定**：Hit/Recall/MRR/nDCG 的边界（K 越界、空相关、并列名次）极易因实现差异产生分歧，纯函数 + 对拍单测是低成本可信保证。
3. **负例要单独归桶**：负例（relevant 为空）若混入「可答查询」会污染兜底率与 IR 指标，需独立统计 `negativeCorrectRate`。
4. **复用生产代码路径**：Runner 直接调 `RagSearchService`/`Reranker` 而非另写检索逻辑，避免「评测通过但线上不生效」的口径偏差。

## 双语检索 · 跨语言向量模型（同日晚追加）

> **主题**：检索能力升级 —— 中文查询可检索英文文档，且支持中英混合语料
> **状态**：✅ 完成，`mvn test` 77/77 通过

### 背景与根因

项目语料几乎全为英文文档，向量模型为百炼 `text-embedding-v4`（1024 维）。该模型虽号称多语言，但**中英向量不在同一语义空间对齐**——中文查询向量与英文文档向量落在向量空间两个区域，余弦相似度普遍偏低，触发兜底（agent.md 坑 #22：「createApp 是做什么的？」触发兜底）。问题不在检索链路/pgvector，而在向量空间的跨语言对齐。

### 方案演进（两阶段，最终收敛到向量对齐）

**第一阶段（已废弃）· 查询翻译**：先落地「中文查询 → DeepSeek 译成英文 → 再向量化」，文档向量零重灌、改动最小。

**转折点**：用户提出「如果知识库里同时有英文和中文文档怎么办」。这暴露了翻译方案的本质缺陷——**翻译只能把查询对齐到单一目标语言**，语料一旦混合，就会反向丢掉另一种语言文档的召回（中文问题译英后召回不到中文文档；英文问题压根不翻译，也召回不到中文文档）。前提假设不成立，方案即失效。

**第二阶段（终版）· 跨语言向量模型**：改用中英共用同一语义空间的向量模型，从根上让向量空间本身对齐，查询期零翻译、代码最简。

| 方案 | 召回覆盖 | 代价 | 结论 |
| --- | --- | --- | --- |
| ① 查询翻译 | 仅单语料有效，混合语料失效 | 每次中文查询多一次翻译调用 | 已删除 |
| ② 跨语言向量模型（**采用**） | 中英混合语料全覆盖 | 一次性重灌向量 + 换 provider | 采用 |
| ③ 多路召回 + RRF 融合 | 全覆盖 | 每次查询 2 次向量检索 + 融合逻辑 | 备选（未采用） |
| ④ 索引期双语化（dual-index） | 全覆盖 | 存储翻倍 + 全量翻译 | 备选（未采用） |

核心原理：跨语言检索只有两条路——**对齐向量空间**（多语言模型）或**对齐语言**（翻译/双语索引）。混合语料下只有前者不需要为每种语言组合打补丁。

### 实现

1. **模型选型**：本地 Ollama + `qwen3-embedding:0.6b`
   - 1024 维（与 pgvector 表一致，**无需改表结构**）、32K 上下文（最大 chunk 3120 token，不截断）
   - 实测中英互译句余弦 **0.9578**，无关中文句 0.3758，中文问 vs 中文无关文档 0.1680
   - 吞吐：batch=8 约 99ms（≈12ms/chunk），3263 条重灌约 1 分钟
2. **配置切换**（`application.yml` / `application-dev.yml`）：
   - `spring.ai.openai.base-url: http://127.0.0.1:11434/v1`（Spring AI 2.0 走官方 OpenAI SDK，**base-url 必须含 `/v1`**）
   - `model: qwen3-embedding:0.6b`（原生 1024 维，**删掉 `dimensions` 配置**，避免向不支持该参数的端点传参）
   - `api-key: ${OLLAMA_API_KEY:ollama}`（Ollama 不校验，仅需非空占位）
   - `docker-compose.yml` 容器内改用 `host.docker.internal:11434/v1` + `extra_hosts: host-gateway`
3. **删除翻译链路**：移除 `rag/QueryTranslator` 与 `QueryTranslatorTest`，`RagSearchService`/`RagTraceService` 恢复原构造函数与直接向量化，诊断结果移除 `translatedQuery`/`queryTranslated`。
4. **全量重灌**：`TRUNCATE kb_chunk, kb_document, vector_store CASCADE` → `--import=all` 从 `data/raw/*.json` 重灌。结果 1443 文档 / 3260 chunk / 3260 向量，10 源 **0 失败**。

### 经验教训

1. **先定位根因再选方案**：「中文搜不到」的根因单一（向量空间未跨语言对齐），但两条路线取舍差异巨大——先问「要不要重灌向量」，这决定改动量数量级。
2. **方案的前提假设要随需求变化重新审视**：查询翻译的前提是「语料单一语言」；需求一变成混合语料，前提即崩塌。**打补丁式方案要明确写出它成立的条件**。
3. ⚠️ **测试脚本的编码陷阱（本次最大坑）**：用 PowerShell 5.1 `Invoke-RestMethod` 传中文 JSON 时，body 默认按非 UTF-8 编码，中文被压成 `?`，导致**同长度中文串变成同一字符串**，测得「无关中文句相似度 = 1.0000」，一度误判为 Ollama 的 CJK tokenization 有 bug、差点放弃整条本地方案。**必须 `[System.Text.Encoding]::UTF8.GetBytes($json)` 传字节并声明 `charset=utf-8`**。教训：**异常完美的数值（恰好 1.0000 / 全同）优先怀疑采集工具，而不是被测对象**。
4. **换 embedding 模型 = 重建全部向量**：新旧向量不在同一空间，混用会让相似度失去意义（重灌前真实文档恒在 0.07 左右）。切换步骤固定为：改配置 → 验证单条 → 清表 → 全量重灌 → 抽样验收 → 跑测试。
5. **本地模型要管存储**：Ollama 默认把模型放 C 盘（`~/.ollama/models`），本次 C 盘写满导致拉取失败。用 `OLLAMA_MODELS` 环境变量改到 D 盘并重启服务；同时 `ollama` 走官方 OpenAI SDK 约定，`base-url` 需带 `/v1`。

### 实现

**A. 分页 + 折叠（决策 D14）**
- 后端 `KbService.docsPage(product, version, source, keyword, page, size)`：`PageResult` + `LIMIT/OFFSET`，与全量 `docs` 共用 `docsWhere` 构造的 WHERE；`total` 用同一组绑定参数做 count；`page≥1`、`size∈[1,100]` 服务端钳制；`GET /api/kb/docs` 返回 `PageResult<KbDocCard>`（默认 page=1 / size=12）。
- **未引入 PageHelper**：Spring Boot 4 无官方兼容 starter，收益不足以承担第三方插件风险，故沿用项目既有 `PageResult`。
- 前端 `KbHome.vue`：`PAGE_SIZE=12`、页码 + 总数 + 上一页/下一页；过滤后页码越界自动回退到最后一页再取一次；左树产品线/版本两级折叠（`+ / −`），展开键用 `product::version` 组合键，避免同名版本互相干扰。

**B. 树高亮 Bug（坑 #36）**
- 根因：高亮判定只比较 `selected.source === s.key`，而 `official` / `community` 在多个产品线下重名，导致全部命中。
- 修复：`isProductActive` / `isVersionActive` / `isSourceActive` 分别要求完整路径匹配（产品线 → 版本 → 来源，且上级未选中），选中下级时自动展开上级。

**C. 会话持久化与会话管理（决策 D15）**
- 表：`kb_conversation(id, username, title, created_at, updated_at)` + `kb_message(conversation_id FK ON DELETE CASCADE, question, answer, found, version, sources JSONB, created_at)`，索引 `(username, updated_at DESC)` / `(conversation_id, id)`。
- `me/ConversationService`：`list`（顺带 `sweepExpired`）、`create`（`INSERT ... RETURNING id`，空标题归一化为「新会话」、截断 60 字）、`detail`、`rename`、`delete`、`append`。**每条 SQL 都带 `username` 条件**，跨用户访问一律 `NotFoundException → code 404`。
- 窗口裁剪：追加后执行 `DELETE ... WHERE id NOT IN (SELECT id ... ORDER BY id DESC LIMIT windowSize)`，只保留最近 10 轮；配置 `app.conversation.window-size` / `ttl-days` 可由环境变量覆盖。
- TTL：`DELETE ... WHERE username = ? AND updated_at < now() - make_interval(days => ?)`，在 `list`/`create` 时顺带执行，消息随会话级联删除。
- 接口：`GET/POST /api/me/conversations`、`GET/PATCH/DELETE /api/me/conversations/{id}`、`POST /api/me/conversations/{id}/messages`（均需登录，401 由 `CurrentUser.username` 统一判定）。
- 前端 `QaHome.vue`：登录用户进入页面自动载入最近会话；会话下拉切换、新建（**首次提问才落库**，避免空会话）、重命名（`ElMessageBox.prompt`）、删除（二次确认）；每轮问答先 `ask` 再 `append`，用后端返回的详情覆盖视图，保证「服务端裁剪后的窗口」与页面一致；持久化失败时退回本地渲染，不阻断回答展示。

**D. 点赞 / 收藏（决策 D16）**
- 表：`kb_doc_like` / `kb_doc_favorite`，复合主键 `(doc_id, username)`，`doc_id` 外键 `ON DELETE CASCADE`；写入用 `ON CONFLICT DO NOTHING` 保证幂等。
- `me/InteractionService`：`like/unlike/favorite/unfavorite` 返回统一 `InteractionResult(likeCount, favoriteCount, liked, favorited)`；文档不存在抛 404。
- 接口：`POST/DELETE /api/me/docs/{docId}/like`、`/favorite`；`GET /api/kb/doc/{id}` 增加 `likeCount/favoriteCount/liked/favorited`（匿名只读计数，状态恒 false）。
- 前端：`KbDoc.vue` 按钮显示「已赞/点赞 N」「已收藏/收藏 N」并按返回状态回填；`Me.vue` 的「我的收藏」渲染真实列表。

**E. UGC 作者归属（决策 D17）**
- 根因：`kb_document` 原本没有作者字段，UGC 发布只写了文档，无法归属。
- 修复：`schema.sql` 幂等 `ALTER TABLE kb_document ADD COLUMN IF NOT EXISTS author TEXT` + 部分索引；`UgcService.publish(req, author)` 在同一事务内 `UPDATE kb_document SET author = ? WHERE id = ?`（失败整体回滚）；`UgcController` 未登录直接 401。
- 新增 `GET /api/me/documents`（`active AND author = ?`）与 `GET /api/me/favorites`（收藏时间倒序），个人中心「我的文档」显示真实数据。

### 经验教训

1. **分页 count 不能只复用 WHERE 字符串**（坑 #35）：最初 `Where.whereOnly()` 只截取 WHERE 子串，既缺 `SELECT count(*) FROM kb_document`，又丢了 `?` 绑定参数，运行时 PostgreSQL 报「未设定参数值」。分页 total 必须与列表**同源同参**；新增分页测试正是为了在无真实 UI 的情况下抓住这类 SQL 拼装错误。
2. **同名方法遮蔽静态导入**：测试里自写 `jsonPath(MvcResult, String)` 辅助方法后，`MockMvcResultMatchers.jsonPath("...")` 的静态导入被实例方法遮蔽，编译器报「参数列表长度不同」并连锁报 34 个错。辅助方法命名避开框架 API（改为 `readPath`）即可。
3. **`@BeforeAll` 早于 Spring 上下文**：静态 `@BeforeAll` 里执行 `DELETE FROM 新表` 时表还没被 `schema.sql` 创建（全新库会直接失败）。建库可放 `@BeforeAll`，**清表必须放 `@BeforeEach`**（此时 JdbcTemplate 已可用）。
4. **会话不在页面加载时落库**：若「新建会话」立即写库，用户点几下就会留下大量空会话；改为首次提问才 `create + append`，列表天然只含真实对话。
5. **窗口裁剪与前端视图要以服务端为准**：前端每轮用 `append` 返回的 `ConversationDetail` 覆盖本地 history，避免「本地 12 轮、服务端 10 轮」的分叉。
6. **树高亮的比较维度要跟数据结构对齐**（坑 #36）：只要 key 在不同父节点下可能重名，高亮/折叠状态就必须用完整路径或组合键，不能只比叶子 key。
